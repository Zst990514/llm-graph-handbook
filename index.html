01

背景：为什么用 LLM 处理图任务

图数据通常同时包含节点与边的关系结构，以及论文摘要、商品描述等文本属性。LLM for Graph 关注怎样利用语言模型的语义理解与指令处理能力，完成节点分类、链接预测、图问答和图生成等任务。

学习主线

LLM for Graph

语言模型帮助图任务：把文本属性编码为节点表示、把图问题转为指令、生成图结构、解释预测，或直接作为图任务求解器。

自然语言 / 文本属性 → LLM → 图表示 / 图预测
先记住一个判断

从具体图任务出发，分别检查文本属性和关系结构提供了哪些信息，再判断语言模型带来的精度、迁移能力或可解释性收益是否值得其编码与推理成本。

领域的五个层次

  1. 数据层：同构图、异构图、知识图谱、文本属性图（TAG）、动态图。
  2. 表示层：图嵌入、文本嵌入、图—文对齐、统一 token / embedding 空间。
  3. 任务层：节点/边/图预测、图问答、多跳推理、图生成与结构化解释。
  4. 系统层：数据构建、图序列化、图—文对齐、Prompt 构造、LLM 推理与结果校验。
  5. 硬件层：稠密 GEMM、图序列编码、不规则数据搬移与长上下文推理。

目标：能表达图的连接关系，理解图序列化的长度与节点顺序，以及基础图算法的数据流。

Attention、MLP、KV cache、prefill/decode、量化、稀疏化、FlashAttention。

目标：能解释训练、prefill 和 decode 的瓶颈为何不同。
03

图任务与评测

节点分类、链接预测、图问答、图生成、训练/验证/测试划分与跨图迁移。

目标：能说明每个任务的输入、输出与质量指标，并检查数据泄漏和泛化能力。

几个容易混淆的概念

知识图谱（KG）和普通图有什么区别？

普通图强调节点与边的连接结构；知识图谱进一步赋予节点、关系明确语义，常用三元组（头实体，关系，尾实体）表示。图问答和图推理系统可以使用 KG，也可以使用文档图、引用图、事件图或运行时构建的图。

文本属性图（TAG）是什么？

Text-Attributed Graph 的节点或边带有自然语言文本。论文引用网络、商品—用户网络、社交网络都可以是 TAG。它要求语义表示与关系结构协同，因此是 LLM for Graph 的重要数据形态。

图嵌入和文本嵌入是一回事吗？

都可以表示为向量，但信息来源不同。文本嵌入强调语义相似性，图嵌入强调邻域、角色或路径结构。融合时必须回答：在哪一层对齐、谁指导谁、结构噪声怎样处理。

03

算法：LLM for Graph

这一主线的问题是：怎样利用 LLM 的语言理解、指令跟随与知识先验，提升图任务的表示、迁移、可解释性或少样本能力。

四种典型角色

角色LLM 做什么典型瓶颈
Predictor把图序列化为文本，直接回答路径、分类或问答任务。上下文过长；对节点顺序敏感；精确图算法不稳定。
Encoder编码节点、边或文档文本，为图任务提供语义向量。大量重复文本编码，成本常高于结构处理本身。
Aligner把图表示与语言空间对齐，支持跨任务迁移与零样本预测。对齐目标、负样本与跨图泛化困难。
Generator / Teacher生成图、标签、解释或伪标注，指导较小图模型。结构合法性、幻觉与验证成本。

代表工作：按问题而不是按年份读

N23NLGraph先回答“LLM 能否用自然语言解决图问题”，适合理解纯 LLM 图推理的边界。NeurIPS'2023 A24Graph Language Models阅读时关注输入图如何表示、模型输出是什么，以及图任务怎样评测。ACL'2024 A24InstructGraph通过图指令数据与偏好对齐增强通用图推理。ACL Findings'2024 N24KG-ICL关注知识图谱场景中的 in-context learning 与结构迁移。NeurIPS'2024 I25Generalization Principles for LLMs on Text-Attributed Graphs理解 TAG 上泛化来自哪里，而不只看单一 benchmark 的精度。ICML'2025
读完应能回答
  • 为什么把邻接表直接写进 prompt 往往不是可扩展方案？
  • 语义编码与关系结构分别贡献了哪些信息？
  • 冻结 LLM、微调 LLM、训练对齐层分别适用于什么资源条件？
04

算法：Graph Foundation Models

图基础模型（GFM）试图用统一模型跨图、跨领域或跨任务迁移。它不是把单一图模型简单放大：真正困难的是不同图之间没有天然统一的节点语义、特征维度、关系类型和标签空间。

三条演进路线

路线 1统一任务表达

把分类、链接预测、图问答等任务转成统一提示或 task tree。

路线 2统一图—文空间

借助 LLM 把节点文本、标签描述与结构表征映射到可迁移语义空间。

路线 3生成式图模型

把节点、边或图操作 token 化，通过生成目标学习结构规律。

R25GOFA面向图上任务的生成式基础模型框架。ICLR'2025 I25GIT: Learning Generalities Across Graphs via Task-Trees通过任务树统一多种图学习任务。ICML'2025 I25Graph Generative Pre-trained Transformer理解图结构如何进入生成式预训练。ICML'2025 PDFGraph Foundation Models: A Comprehensive Survey系统梳理 GFM 的定义、模型、数据与评测。arXiv'2025
读论文时重点检查
  • “跨图”是否只是在相似数据集之间迁移？
  • 是否依赖节点文本；没有文本时还能否工作？
  • 统一的是模型参数、提示空间、任务接口，还是数据模式？
  • 大模型带来的增益是否值得其编码与推理成本？
05

系统：端到端协同怎样拆

做体系结构研究前，先画清在线与离线边界。只优化一个 kernel，而它在真实流水线中占比很小，通常难以形成有说服力的端到端收益。

离线文本 / 图数据摄取解析、实体抽取、关系抽取、消歧、图构建
离线 + 训练图—文表示LLM 编码、结构编码、模态投影与对齐目标
在线结构转换图序列化、结构 token、路径或规则表达
在线图任务预测节点分类、链接预测与图问答
在线生成与验证Prompt 编排、LLM prefill/decode、结构与事实校验

阶段—计算—硬件特性对照

阶段核心操作主要特性
文本编码GEMM、Attention、LayerNorm算力/带宽混合；适合 GPU/NPU，批量影响巨大
结构转换序列化、重编号、结构 token 化数据相关控制流明显，序列长度随图规模变化
图—文对齐投影、对比目标、交叉注意力不同表示空间间的数据搬移与同步开销明显
图任务预测分类头、节点对打分、图指令推理输出规模与计算模式随任务类型变化
LLM 生成prefill + 自回归 decodeprefill 偏计算；decode 偏权重/KV 访存
评测原则

报告端到端延迟，并同时给出数据规模、图度分布、路径长度、文本长度、输出 token 数、任务精度和预处理成本。缺少这些条件的“倍数加速”很难横向比较。

06

硬件：Transformer / LLM 推理加速

在 LLM for Graph 中，Transformer 可能承担节点文本编码、图序列建模和最终生成。三种角色的批量、序列长度与重用模式不同，不能用同一套加速假设。

先掌握的三类优化

  1. IO-aware：减少 HBM 与片上 SRAM 之间的数据搬移，代表是 FlashAttention。
  2. 稀疏与裁剪：减少 token、head 或位级计算，但需要处理不规则性和精度损失。
  3. 量化与存内/近存：降低权重与 KV 的位宽或把乘加移近存储，重点是精度、可编程性与数据流。
N22FlashAttention用 IO 复杂度理解 attention 优化的经典入口。NeurIPS'2022 H21SpAtten级联 token/head 剪枝与稀疏 attention 架构。HPCA'2021 H22TransPIM理解 Transformer 近存处理的数据布局与算子映射。HPCA'2022

补充课程：MIT 6.5940 EfficientML / TinyML。前几讲适合建立剪枝、量化、稀疏与数据流基础。

07

学习计划：从入门到能读系统论文

下面是一条建议顺序。时间只是参考；判断是否进入下一阶段，应看能否完成对应产出。

第 1–2 周

基础计算

  • 实现 BFS、最短路与多跳关系组合。
  • 画出 Transformer attention 的张量形状与访存。
  • 比较三种图序列化顺序对 token 长度的影响。
产出：3 张数据流图 + 1 份术语表
第 3–4 周

算法范式

  • 精读一篇 LLM for Graph survey。
  • 选择 NLGraph / InstructGraph / KG-ICL 之一复现实验。
  • 比较文本序列化、结构提示与图—文对齐三种范式。
产出：10 分钟组会导读 + 可运行 notebook
第 5–8 周

系统剖析

  • 搭一个最小图问答或图生成流水线。
  • 分别测编码、结构转换、图任务预测与 prefill/decode。
  • 改变图规模、路径长度、文本长度和输出长度。
产出：端到端 profile 与瓶颈归因
第 9–12 周

硬件阅读

  • 按 FlashAttention→SpAtten→TransPIM→GFMEngine 顺序阅读。
  • 每篇只回答：任务、瓶颈、关键机制、代价、评测是否充分。
  • 把论文机制映射回自己的 profile。
产出：一张算法—算子—硬件对照图

论文精读模板

  1. 它解决的真实任务是什么？输入、输出和质量指标是什么？
  2. 基线系统的端到端瓶颈在哪里？占比怎样测得？
  3. 核心机制改变了数据表示、执行顺序、复用还是精度？
  4. 额外付出了什么：面积、能耗、预处理、存储、更新或质量损失？
  5. 数据集、图规模、模型规模和参数是否覆盖真实场景？
  6. 如果换成动态图、长文本、强谓词或更大 LLM，结论是否成立？

总结

从图任务出发，明确语言模型能帮助解决什么问题；选择合适的算法范式；拆解成编码、结构转换、预测与生成的计算特性；最后才讨论采用怎样的系统与硬件协同。

01

学习主线是 LLM for Graph、图基础模型，以及对应的系统与硬件加速。

02

先验证语言模型对图任务的精度和泛化贡献，再评估额外的训练与推理成本。

03

不要只看 kernel 加速；端到端系统还包括构图、表示转换、搬运、推理、生成和校验。
